# NVMeVirt validation kit — ZNS vs conventional SSD for agentic-LLM offloading

Reproduces the simulation study on **real hardware** using NVMeVirt
(FAST'23, `github.com/snu-csl/nvmevirt`), which emulates NVMe devices at the
PCI level inside the kernel with published fidelity of ≤11.8 % (conventional
SSD) and ≤3.3 % (ZNS) vs. real devices.

Target machine: `alex@192.168.1.83` (x86_64 Linux, ≥64 GiB RAM recommended;
32 GiB works with smaller `memmap`).

## 1. One-time setup (reserve memory for the virtual devices)

```bash
sudo vim /etc/default/grub
#   GRUB_CMDLINE_LINUX="memmap=48G\\$16G"     # reserve 48 GiB starting at 16 GiB
sudo update-grub && sudo reboot
cat /proc/cmdline    # verify memmap is present
```

Pick sizes to fit your RAM: the study needs two 16–24 GiB virtual devices
(one conventional, one ZNS — they can be loaded one at a time with a single
reservation).

## 2. Build both device personalities

```bash
./build.sh           # clones nvmevirt @ 61c90f7, builds nvmev_conv.ko and nvmev_zns.ko
```

`build.sh` edits `Kbuild`: conventional = `CONFIG_NVMEVIRT_SSD` (Samsung
970 Pro profile, full FTL with GC), ZNS = `CONFIG_NVMEVIRT_ZNS`
(`BASE_SSD=WD_ZN540` profile). To match the paper's 7 % OP, `build.sh` also
patches `ssd_config.h` (`OP_AREA_PERCENT 0.07`) — see the script.

## 3. Run

```bash
# conventional target
sudo ./load.sh conv 16G 48G "0,1"      # memmap_start memmap_size cpus
lsblk                                   # note the new /dev/nvmeXnY
make replayer
gunzip -k ../traces/tr_occ90.txt.gz
sudo ./replayer -t ../traces/tr_occ90.txt -d /dev/nvmeXnY -m conv -o out_conv -s 0.25

sudo rmmod nvmev
sudo ./load.sh zns 16G 48G "0,1"
sudo ./replayer -t ../traces/tr_occ90.txt -d /dev/nvmeXnY -m zns -o out_zns -s 0.25
```

`-s 0.25` replays the 7,800-virtual-second trace 4x faster (~33 min); use
`-s 1` for full-fidelity think times. The replayer prints the same
`LAT <class> ... p99_us ... p999_us` summary lines as the simulator, so the
comparison table can be regenerated by pointing `sim/plots.py` at the outputs.

## What to expect

The simulator (FEMU-lineage FTL model) predicts, at ~0.86 steady-state
occupancy: conventional-SSD agent-memory 4 KiB read p99 in the tens of ms
(GC-blocked LUNs) vs. low ms on ZNS (≥10x), device WAF ~2.5 vs ~1.0.
NVMeVirt's conventional FTL implements the same greedy-GC design lineage, so
directionally identical behavior is expected; absolute numbers will shift
with its Samsung-970Pro timing profile.

## Files

- `replayer.c` — trace replayer (O_DIRECT, 128 KiB commands, POSIX AIO QD32,
  extent allocator + BLKDISCARD in conv mode; zone-per-session +
  BLKRESETZONE + host index compaction in zns mode)
- `build.sh`, `load.sh` — NVMeVirt build/load helpers
- `Makefile` — builds the replayer
- `../traces/tr_occ90.txt.gz` — the exact trace used in the paper (occ-0.86)
- `../sim/` — the simulator, to regenerate traces at other occupancies

## Caveats

- ZNS mode requires kernel ≥5.10 with `CONFIG_BLK_DEV_ZONED`.
- If `insmod` panics in `__pci_enable_msix()`, add `intremap=off` to grub
  (NVMeVirt README, IOMMU incompatibility).
- Intra-zone writes run at QD1 (zone write-pointer rule); reads at QD32,
  matching the simulator's settings.
